## Première tranche de présentation recommandée

Raccorder les tokens via l'adaptateur de thème existant, puis les primitives existantes et le rendu du catalogue : toile gris doux, surfaces opaques claires/sombres, séparateurs fins, rayons champ 12/carte 20/feuille 28, chiffres tabulaires, bouton et focus lisibles. Le ticket conserve son panneau ancré/tiroir, les prix calculés et tous les moyens de paiement. Le catalogue peut augmenter la place de la photo dans sa carte sans changer son URL ni son cadrage, dans les bornes de densité du layout existant.

La référence RestoPilot montre un rail de navigation, un grand champ recherche, des catégories en capsules, trois colonnes de produits illustrés et un ticket droit. Le kit ajoute les comportements connus de Snack Manager (trois paiements, téléphone et fidélité). Leur contenu de démonstration et le seul bouton « Envoyer en cuisine » de RestoPilot ne définissent pas le périmètre du POS. Ne pas supprimer B/C ni transformer le processus de paiement pour reproduire cette capture.

Périmètre à privilégier : `theme.ts`, styles `ui.tsx`, styles de `Catalog.tsx`, `CategoryTabs.tsx`, `TicketPanel.tsx`, `TopBar.tsx`. Exclure toute réécriture des handlers `PosScreen`, des composants modaux, des calculs, stores ou contrôleurs pour ce premier lot. Faire les surcouches configuration/service/paiement dans une tranche suivante après validation visuelle de la vente.

## Recette proposée, commandes non exécutées par cet audit

Scripts lus : `apps/pos/package.json`, `e2e/lancer.mjs`, `e2e/socle/cibles.mjs`, `scripts/verifier-build-terrain.mjs`. Le monorepo déclare Node `>=24.12.0`, pnpm `10.14.0`. Ne pas utiliser le script lint POS (« echo ok ») comme preuve d'analyse statique.

Depuis la racine, avec les dépendances et la version Node du dépôt disponibles :

```sh
EXPO_PUBLIC_API_URL=http://localhost:3001 EXPO_PUBLIC_ALLOW_LOCAL_API=1 EXPO_PUBLIC_SITE_URL=http://localhost:3000 pnpm --filter @sm/pos test
pnpm --filter @sm/pos typecheck
EXPO_PUBLIC_API_URL=http://localhost:3001 EXPO_PUBLIC_ALLOW_LOCAL_API=1 EXPO_PUBLIC_SITE_URL=http://localhost:3000 pnpm --filter @sm/pos build
```

Après démarrage du POS construit avec ces origines locales, les tests démonstration ciblés peuvent être lancés sans API réelle :

```sh
SM_E2E_CIBLE=local SM_E2E_POS=http://localhost:8082 SM_E2E_API=http://localhost:3001 SM_E2E_WEB=http://localhost:3000 SM_E2E_CAPTURES=docs/refonte-ui/captures/pos node --test e2e/demo/caisse.test.mjs e2e/demo/caisse-preferences.test.mjs e2e/demo/caisse-demarrage-encaissement.test.mjs
```

Adapter explicitement le port à celui réellement choisi, sans changer l'origine API/site du build. Ne pas lancer `pnpm e2e` sans cible : le défaut actuel est staging, et la série « réel » est incluse sans `--demo`.

Les deux scripts `e2e/local/pos-counter-payment.mjs` et `e2e/local/pos-phone-order.mjs` utilisent un transport intercepté local ; lire leur contenu complet et leurs prérequis avant exécution. Le script téléphone fabrique un bundle de test ; son résultat ne remplace pas le build Expo de l'application. Le script encaissement impose une origine POS localhost/127.0.0.1.
